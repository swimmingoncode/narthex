# Rulings of 2026-10-17 (Pablo, in chat)

Given in reply to `notes/2026-10-17-product-definition-review.md`. Recorded here so that the rewrite of SPEC.md
cites them; quotes are Pablo's words, lightly trimmed.

| # | Ruling |
|---|---|
| R1 | **The name "SDD Studio" is dropped.** Use codenames until a final name is found; brainstorm candidates. |
| R2 | **Assess the user's experience at intake**, alongside the sector: a casual vibe-coder or a professional engineer. |
| R3 | **Interface: MCP and a GUI.** The GUI is web, with optional harness add-ons (e.g. Claude Desktop plugins). The MCP hands the user links into the UI, so people work in a friendly interface instead of the chat, which "clobbers users' thinking process through excessive text". Open question: can a Claude Desktop plugin tell the agent about the user's input (e.g. a submit click)? |
| R4 | **Sector material:** open standards' text may be shipped. Where only an open implementation or non-normative documentation exists, ship checklists, mappings and guidance, explicitly labelled supplementary, not normative. Closed standards are "early preview / available soon", or fall back to "our standard way". |
| R5 | **The product specification is the most important input.** The level of guidance depends on the user: for non-engineers, the user's agent asks a set of questions (we provide the knowledge base) to steer them to a proper product spec; for engineers, a shorter questionnaire, an AI-reprocessed prompt or a standard form. Producing the product spec stays out of scope as a separate product (from the earlier definition). |
| R6 | **A book.** Pablo plans a book on the whole system, so anyone can build something similar. Collect references and bibliography for everything. |
| R7 | **Repositories:** GitHub, GitLab and Codeberg integrations are planned features (user-owned repos, SDD Studio as an app). |
| R8 | **The MCP surface** (knowledge, spec data, change, verify, decide) is ruled. Plus: skills periodically check and update the task queue, or tell the user's main agent to use its built-in task tools, because agents forget to update the form's queue, archive and respond. Each read of the form through the MCP returns only the items changed since the previous read, and tells the agent to update the form at the end of the iteration. |
| R9 | **No natural-language agent layer of our own for now.** Later. |
| R10 | **Multiple teams** as proposed: identifier ownership per team, decision routing per role, amendment conflict handling, one shared methodology store with per-team overrides. Ruled. |
| R11 | **Low-code and no-code** as proposed: same component spec, verification by contract tests, built by builders. Ruled. |
| R12 | **First customers, in order:** (1) Bloque's teams, not all of them software engineers; (2) individual engineers, emphasis on engineers in general (a civil engineer, a self-taught coder), not only software engineers; (3) software factories and consultants last: they bring the most variability and need it least, and can read the book. |
| R13 | **Sign-up profiles the user.** A complete newcomer signs in with Google, Outlook or email, or runs on delegated infrastructure (e.g. Claude cloud), and is guided to set up a GitHub account. Others sign in with GitHub, GitLab or Codeberg (more later) as the registration step. |
| R14 | **Minimal product-spec input contract:** adopted. |
| R15 | **The chain** adds architecture and design, security and threat modelling, verification and validation, release and operations, evolution, and compliance evidence throughout. Adopted. |
| R16 | **Sector material** as in R4. |
| R17 | **Decision inbox:** see R3 and R8 (UI linked from the MCP; incremental reads). |
| R18 | **Rewrite SPEC.md now**, folding in research, prior art, amendments 0001–0005 and the recommendations. |
| R19 | **Restart amendment numbering** after the rewrite. Amendments 0001–0005 are history, not carried as numbered amendments. |
| R20 | **Authenticated links, split by purpose** (refined by Pablo the same day). Reading the form's state uses a short-lived token. Filling out the form uses a long-lived, narrowly scoped token: one form, submit answers only, revocable. A short-expiring link that dies while someone takes hours to think is "a recipe for disaster". Refreshing the form's state needs a browser session or a login; otherwise the long-lived token may ask the agent to produce a fresh link. The MCP suggests the agent open links in the harness's own browser when there is one. |
| R21 | **Layered delivery of answers:** first, where available, a plugin with hooks that brings the user's answer back to the agent; otherwise a standard link, and the agent waits and asks again. |
| R22 | **Unattended is the norm.** Pablo moves between projects and other work, so a form can sit unanswered for a long time. The agent doesn't poll. It opens a monitor where the harness has one. If no channel is open, it tells the user to come back and acknowledge it once they've answered. Meanwhile it carries on with other work. |
| R23 | **Narthex generates its own published pages** (Pablo, 2026-10-17, "special emphasis"). The decision form and the HTML editions are published as claude.ai artifacts for now. In the finished product, Narthex itself generates them and they don't live on Claude exclusively. |
