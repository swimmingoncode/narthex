# Intake: specsite, the living-docs layer, already being built

2026-10-12. Relayed by the aledgent session at Pablo's request ("feed ALL of this to SDD Studio. Clearly, we're
building something bigger than us."). The aledgent session dates these events 2026-10-13.

## What exists

- **aledgent's public docs site:** Starlight (Astro) with Bloque's theme, Pagefind search, and starlight-openapi.
  `openapi.json` is generated from code and checked in CI, so the API reference cannot drift (aledgent PR #234).
- **HTML editions of SPEC, PLAN and OVERVIEW:** a one-off generator in
  a local checkout (`md2artifact.py`, `build.sh`, `mermaid.lua`).
  It renders the Markdown with pandoc inside a branded shell, with a contents rail and light and dark themes.
  Every requirement id is an anchor where it is defined and a link everywhere else, across documents. The
  editions (aledgent Spec, Plan and Overview; bezent Spec) are published as private pages.
- **specsite** (public repo `swimmingoncode/specsite`, named by Pablo; v0.1 in progress on `feat/v0.1`):
  - a Starlight plugin that loads an explicit list of repo-root Markdown files (SPEC, PLAN, OVERVIEW,
    amendments) at build time, optionally splitting each by H2;
  - it anchors each requirement id where it is defined, links every mention across pages and documents, and
    rewrites links between the listed documents;
  - it shows "Source: SPEC.md @ commit" with edit links, and is searchable with Pagefind;
  - a CLI, `specsite html`, writes the single-file HTML edition (a port of `md2artifact.py`, so there is one
    implementation);
  - MIT (since 2026-10-12, under Swimming on Code), DCO, CI, and a test fixture with invented content. It will first be proven in aledgent's
    docs site.

## Pablo's principles, as relayed

1. **The `.md` is still the source of truth.** Specs become living documents, generated on each project's site,
   never copied by hand.
2. **A tool that other projects need is a public repo; if one already exists, use it.**

## Prior art the aledgent session checked

- **sphinx-needs** and **StrictDoc**: typed requirements with ids, links, enforced fields and trace tables
  (`needs.json` export). Both need each requirement written as a structured block, whereas our specs write
  `**REQ-AU-8**` inline in prose; adopting either means rewriting the format and running Sphinx beside
  Starlight.
- The commercial incumbents are IBM DOORS, Jama and Polarion. The standards that ask for traceability are
  process standards: DO-178C, ISO 26262, IEC 62304.
- Nothing renders a repo's Markdown specs in Starlight with requirement-id linking. Hence specsite.
- The aledgent session's suggestion, not yet ruled: keep specsite small and our Markdown as it is, but add a
  `needs.json`-compatible export so audits and regulators' tools can read our requirements.

## What it means for SDD Studio

specsite **is** module LD (§6) taking shape, and it was built from a real need rather than from our spec:

| SPEC requirement | specsite v0.1 |
|---|---|
| `REQ-LD-1` HTML from a named commit | Yes: site, plus `specsite html` for a single file |
| `REQ-LD-2` basis block | "Source: SPEC.md @ commit" |
| `REQ-LD-3` anchors from identifiers | Yes, at the definition |
| `REQ-LD-7` identifiers in text become links | Yes, across documents |
| `REQ-LD-4` tombstones for withdrawn ids | Not mentioned |
| `REQ-LD-5`, `REQ-LD-6` backlinks to decisions, peek from the form | Not yet: needs `decisions/` as an input |
| `REQ-LD-8` broken-reference and duplicate checks | Not mentioned |
| `REQ-LD-9` PDF | Not mentioned (the HTML edition comes first) |
| `REQ-LD-11` spec version with its amendments | Partly: amendments are inputs |

Our open questions `OQ-13` (renderer), `OQ-14` (where docs are published) and `OQ-17` (PDF in v1) are mostly
answered by what was built: Starlight with a pandoc-based HTML CLI; project sites plus private artifact
editions; HTML first.

What SDD Studio needs from specsite, in order:

1. Read `decisions/questions.json`, `decisions/responses/` and `amendments/`, and show at each anchor the
   items and amendments that reference it: the backlinks (`REQ-LD-5`, `INV-6`).
2. A broken-reference and duplicate-id check that fails the build (`REQ-LD-8`); Kippu's `features.py check`
   is prior art.
3. Tombstones for withdrawn ids (`REQ-LD-4`).
4. The HTML edition published next to the decision form, so items open spec sections in place (`REQ-LD-6`).
   The form's peek already reads any page with id anchors.
5. Later: links from code and tests to requirement ids, coverage, and the `needs.json` export.

## Candidate: on-brand diagrams (added 2026-10-17)

[diagram-design](https://github.com/cathrynlavery/diagram-design) (MIT) is an agent skill that draws 45 diagram
types as self-contained HTML and SVG in a site's brand, and imports Mermaid, draw.io and Excalidraw. specsite
renders Mermaid on the client today. A later version could take the diagrams from it, or recommend it for
documents' diagrams, with the Swimming on Code palette and fonts. Not on the roadmap yet.
