# SDD Studio: landscape research (2026-10-03)

Scope: (1) spec-driven development (SDD) tools for AI agents, (2) decision-record tools and processes, (3) Claude Code skills and plugins as a way to package SDD Studio. Every claim links to a source. Claims marked **[unverified]** come only from secondary sources, or the sources disagree.

---

## 1. Spec-driven development tools

Böckeler (Thoughtworks, on martinfowler.com, 2025-10-15) sorts SDD tools into three levels. In **spec-first**, the spec is written before the code. In **spec-anchored**, the spec is kept and maintained after the task ships. In **spec-as-source**, the spec is the main artifact people edit. She places Kiro and Spec Kit at spec-first only and Tessl at spec-anchored, exploring spec-as-source. Her criticisms: too much repetitive markdown to review, heavy ceremony on small tasks (a small bug fix became "4 user stories with … 16 acceptance criteria"), agents that still ignore the specs, and no clear story for keeping specs up to date. [martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

### GitHub Spec Kit
- **Artifacts:** `constitution.md`, `spec.md`, `plan.md`, `tasks.md`. Opt-in extensions add bug and idea assessments under `.specify/`. [repo](https://github.com/github/spec-kit)
- **Flow:** `/speckit.constitution → specify → clarify → plan → tasks → analyze → implement`. [Augment guide](https://www.augmentcode.com/guides/github-spec-kit-practical-guide-sdd-workflow)
- **Open questions:** the spec carries `NEEDS CLARIFICATION` markers. `/speckit.clarify` then asks **at most 5 questions per session, one at a time**. Each question is either multiple choice (2–5 options, with a **Recommended** option and its reasoning shown first) or a short answer of 5 words or fewer with a **Suggested** default. Each answer is appended as `- Q: … → A: …` under `## Clarifications / ### Session YYYY-MM-DD` and also merged into the relevant spec sections. [clarify.md template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
  - This is the closest existing thing to "questions with defaults". It is still a chat exchange, though: answers end up as markdown bullets, not structured data.
- **Amendments:** only the constitution is versioned. It uses semver (MAJOR, MINOR, PATCH), `RATIFICATION_DATE` and `LAST_AMENDED_DATE`, plus a "Sync Impact Report" HTML comment that is meant to be deleted before commit. [constitution.md template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/constitution.md). I found no amendment or change tracking for feature specs **[unverified absence]**.
- **Packaging:** a Python CLI `specify-cli` (`uv tool install specify-cli`) that installs slash commands for each agent. Over 30 agent integrations as of June 2026, including Claude Code. **MIT.** [repo](https://github.com/github/spec-kit), [Augment](https://www.augmentcode.com/guides/github-spec-kit-practical-guide-sdd-workflow)

### AWS Kiro
- **Artifacts:** `requirements.md` (user stories plus EARS acceptance criteria) or `bugfix.md`, then `design.md` (architecture, sequence diagrams) and `tasks.md`. Kiro updates task status live, and independent tasks run in dependency "waves". [Kiro docs: specs](https://kiro.dev/docs/specs/index)
- **Open questions:** an "Analyze Requirements" step flags ambiguities and gaps before design. The docs don't say how. [Kiro specs](https://kiro.dev/docs/specs/index)
- **Steering:** `.kiro/steering/` holds `product.md`, `tech.md` and `structure.md`. Files can load always, on a fileMatch glob, manually, or automatically by description. AGENTS.md is also supported. [Kiro steering](https://kiro.dev/docs/steering/)
- **Hooks:** JSON files in `.kiro/hooks/`. Triggers include file save, create and delete, `Pre/PostToolUse`, `Stop`, and manual runs. A hook runs either a shell command or an agent prompt. [Kiro hooks](https://kiro.dev/docs/hooks/)
- **Packaging and license:** a proprietary IDE built on Code OSS, plus a CLI. Credit-based pricing (Free, $20, $40, $200 tiers), and spec requests cost more than vibe requests. [pasqualepillitteri.it](https://pasqualepillitteri.it/en/news/6370/amazon-kiro-ide-spec-driven-review), [The Register](https://www.theregister.com/2025/08/18/aws_updated_kiro_pricing/). The GA date and tier details are **[unverified]** (secondary sources only).
- **Amendments:** no versioning or change log for specs. They are edited in place **[unverified absence]**.

### OpenSpec (Fission-AI)
- **Artifacts:** `openspec/specs/` holds the current source of truth. Each change lives in `openspec/changes/<id>/` with `proposal.md`, `design.md`, `tasks.md` and **delta specs**. [repo](https://github.com/Fission-AI/OpenSpec)
- **Change tracking (its strongest feature):** a delta spec has `ADDED`, `MODIFIED` and `REMOVED` Requirements sections. Requirements use SHALL/MUST wording with Given/When/Then scenarios. `archive` merges the deltas into `specs/` and moves the change folder to `changes/archive/` with a date prefix. [concepts.md](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/concepts.md)
- **Open questions:** no dedicated structure. The docs only say "update any artifact anytime". [concepts.md](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/concepts.md)
- **Packaging:** npm `@fission-ai/openspec` or Homebrew. Slash commands `/opsx:explore|propose|apply|archive` (more in an extended profile) across 30+ tools. **MIT.** [repo](https://github.com/Fission-AI/OpenSpec)

### Tessl
- **What it is:** a spec-anchored / spec-as-source framework that plugs into existing agents over MCP, plus a registry. The registry went to open beta on 2025-09-16 as a spec registry and reportedly became a "Skills Registry" in January 2026, with the framework still in closed beta **[unverified, secondary sources]**. [rywalker.com](https://rywalker.com/research/tessl), [codemyspec review](https://codemyspec.com/blog/tessl-review), [registry](https://tessl.io/registry/tessl-labs/spec-driven-development)
- **License:** commercial platform. I found no OSS license for the framework **[unverified]**.

### BMAD-Method
- **Artifacts:** product brief, PRD, UX spec, architecture, then epics and stories (in v6, epics are written *after* architecture), plus story files. Uses named persona agents (PM, Architect, SM, Dev, and others). [Augment guide](https://www.augmentcode.com/guides/bmad-method-ai-development)
- **Amendments:** the `correct-course` workflow checks drift against the PRD, epics and architecture, then produces a "Sprint Change Proposal". [skillselion](https://skillselion.com/skills/bmad-code-org/bmad-method/bmad-correct-course)
- **Packaging:** `npx skills add …`, a Claude Code plugin marketplace (`/plugin marketplace add bmad-code-org/bmad-plugins`) and a Codex plugin. **MIT.** [repo](https://github.com/bmad-code-org/BMAD-METHOD)

### Agent OS (Builder Methods)
- **Artifacts:** codebase "standards" (discover, deploy, index) and "shape spec" (spec shaping during plan mode, with "shaping questions"). Mainly Claude Code commands; also works with Cursor and others. **MIT.** [site](https://buildermethods.com/agent-os), [repo](https://github.com/buildermethods/agent-os)

### Built-in plan modes
- **Claude Code:** plan mode can read files and run shell commands to explore, but edits are blocked until the plan is approved. `Ctrl+G` opens the plan in an editor. Enter it with `Shift+Tab`, `/plan`, or `--permission-mode plan`. [docs](https://code.claude.com/docs/en/permission-modes). The `AskUserQuestion` tool asks multiple-choice questions with an "Other" free-text option. By default questions wait for an answer, or they can auto-continue after a timeout (`askUserQuestionTimeout`). [tools reference](https://code.claude.com/docs/en/tools-reference)
- **Cursor:** plan mode (October 2025) asks clarifying questions and writes a markdown plan with to-dos in `.cursor/plans/`, which you can save into the workspace. [Cursor docs](https://cursor.com/docs/agent/plan-mode), [blog](https://cursor.com/blog/plan-mode)
- Neither keeps decisions or plans as durable, linked records.

### Adjacent: KanBots (decision prompts)
- Agents emit a structured event: question, numbered options, and a **default**. The answer is a click on a kanban card and goes back to the agent over stdin. A default is applied automatically after a timeout (24 h by default). Every decision is logged with its question, options, chosen value, who resolved it (or the timeout), and a timestamp. **MIT.** [kanbots docs](https://kanbots.dev/docs/decision-prompts)
- This is the closest prior art to SDD Studio's decision inbox. It is board-centric and its decisions aren't linked to spec or requirement anchors **[unverified, docs only]**.

### What the existing tools leave out (where SDD Studio fits)
| Gap | Current state |
|---|---|
| Decisions stored as structured data with an answer UI | Spec Kit's clarify writes Q→A bullets in markdown, chat only. KanBots has a click-UI but nothing tied to specs. Kiro and OpenSpec have no decision object. |
| Requirement ↔ decision ↔ task traceability | Kiro and Spec Kit link tasks to the spec loosely, through prose. OpenSpec groups proposal, deltas and tasks per change. None has stable IDs or anchors linking all three. |
| Living, rendered docs with backlinks | All of these are raw markdown in the repo. None renders a site with backlinks from spec sections to the decisions that shaped them (ADR tools render decisions alone; see §2). |
| Amendments to accepted specs | Only OpenSpec (delta specs plus archive) and Spec Kit's constitution (semver) handle this. Nobody tracks supersession for individual decisions. |
| Lead-to-many-agents dispatch and reports | Kiro has task waves and BMAD has an SM/Dev loop. Neither has an outbox: dispatch, then a structured report back to the lead. |
| Right-sizing | All four (Kiro, Spec Kit, OpenSpec, BMAD) are criticized as too heavy for small tasks (Böckeler). BMAD and OpenSpec now advertise scale-adaptive or "no phase gates" modes. |

## 2. Decision-record tools and processes

- **Nygard ADR (2011):** Title, Context, Decision, Status, Consequences. Statuses: proposed, accepted, deprecated or superseded. A superseded ADR is kept, marked as superseded, and points to its replacement. Meant to be 1–2 pages. [Cognitect](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
- **MADR 4.0.0 (Sept 2024):** YAML front matter (`status`, `date`, `decision-makers`, `consulted`, `informed`). Sections: Context and Problem Statement, Decision Drivers, Considered Options, Decision Outcome, Consequences, **Confirmation**, and Pros and Cons of the Options. Statuses: proposed, rejected, accepted, deprecated, superseded. Files are named `NNNN-title.md`. MIT or CC0. [MADR](https://adr.github.io/madr/)
- **adr-tools:** shell CLI with `adr init`, `adr new`, `adr new -s N` (supersede: rewrites both files' status lines with cross-links), `adr link`, and `adr generate toc|graph`. **GPL.** [repo](https://github.com/npryce/adr-tools)
- **log4brains:** ADRs as docs-as-code, with interactive creation from the CLI, hot-reload preview, and a **static site** (searchable timeline). Supports monorepos, uses MADR by default, and pulls metadata from git. Records are immutable except for their status. **Apache-2.0.** [repo](https://github.com/thomvaill/log4brains)
- **Backstage ADR plugin:** the `backstage.io/adr-location` annotation attaches an ADR folder to a catalog entity. Parses MADR 2.x/3.x. A search collator indexes ADRs. Community-maintained. [backend README](https://github.com/backstage/community-plugins/blob/master/workspaces/adr/plugins/adr-backend/README.md), [Roadie](https://roadie.io/docs/integrations/adr/)
- **Structurizr:** `!adrs <path> [adrtools|madr|log4brains]` imports ADRs into a workspace, system or container, and the UI has a decisions section. I could not confirm decision-graph rendering from the docs **[unverified]**. [docs](https://docs.structurizr.com/dsl/adrs)
- **RFC/RFD processes:**
  - **Rust RFCs:** PR-based. A template with an "Unresolved questions" section, a 10-day Final Comment Period, then merged, postponed or closed, plus tracking issues. [rust-lang/rfcs](https://github.com/rust-lang/rfcs)
  - **Oxide RFDs:** states prediscussion → ideation → discussion → published → committed, or abandoned. Discussion happens in PRs. A shared rendering site and short URLs. [RFD 1](https://rfd.shared.oxide.computer/rfd/0001)
- **"Questions with defaults answered through a form":** I found no ADR tool that does this. The nearest matches are Spec Kit `clarify` (recommended option, chat only), Claude Code `AskUserQuestion` (multiple-choice UI, session only, not saved), and KanBots decision prompts (default plus timeout plus audit log). The plugin `userConfig` schema (typed fields, `options`, `default`, `required`) is a ready-made shape for form fields. [plugin manifest ref](https://code.claude.com/docs/en/plugins-reference)

**Shared patterns to reuse:** a status lifecycle (proposed → accepted, rejected, deprecated or superseded), immutable bodies where only the status changes, two-way supersede links (adr-tools, log4brains), numbered file names, YAML front matter (MADR), and static-site rendering with search (log4brains, Backstage).

## 3. Claude Code skills and plugins as packaging

### SKILL.md ([docs](https://code.claude.com/docs/en/skills))
- **Layout:** one directory per skill: `SKILL.md` (YAML front matter plus markdown) and optional supporting files such as `reference.md` and `scripts/` (scripts are run, not loaded into context). Keep `SKILL.md` under 500 lines.
- **Front matter:** `name`, `description` (combined with `when_to_use`, truncated at 1,536 chars), `argument-hint`, `arguments`, `allowed-tools`, `disallowed-tools`, `disable-model-invocation`, `user-invocable`, `model`, `effort`, `context: fork` + `agent`, `paths`, `hooks`, `metadata`, `license`, `compatibility`.
- **Progressive disclosure:** only the name and description sit in context. The body loads when the skill is invoked, and supporting files load only when referenced. After compaction, each skill keeps its first 5,000 tokens, within a 25,000-token budget shared by all skills.
- **Dynamic context:** `` !`cmd` `` injects command output before the model sees the skill. Substitutions include `$ARGUMENTS`, `$name`, `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}`.
- **Portability:** for claude.ai or the Skills API, restrict front matter to the Agent Skills spec fields (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`); Claude Code-specific fields cause upload errors. Agent Skills became an open standard (agentskills.io) in December 2025 and has been adopted by Codex, Gemini CLI, Cursor, Copilot and others **[secondary source]**. [VentureBeat](https://venturebeat.com/ai/anthropic-launches-enterprise-agent-skills-and-opens-the-standard)

### Plugin structure ([manifest ref](https://code.claude.com/docs/en/plugins-reference))
- **Manifest:** `.claude-plugin/plugin.json` is optional, and `name` (kebab-case) is the only required field. Optional fields include `version`, `description`, `author`, `license`, `dependencies`, `userConfig`, `defaultEnabled`, and component path overrides.
- **Default layout:** `skills/<name>/SKILL.md`, `commands/` (legacy, so prefer skills), `agents/`, `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `output-styles/`, `workflows/`, `monitors/`, `bin/` (added to the Bash PATH), and `settings.json` (only `agent` and `subagentStatusLine` take effect).
- **Namespacing:** every component lives under the plugin name, so skills are invoked as `/sdd-studio:spec`.
- **Name rules:** names starting with `claude-`, `anthropic-` and similar are reserved.
- **Persistent state:** `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/<id>/`) survives updates. `${CLAUDE_PLUGIN_ROOT}` changes with each version, so nothing durable should be written there.
- **Containment:** every path must stay inside the plugin root. `..` and symlinks that lead outside are rejected, and files outside the plugin directory aren't copied into the cache. [loading ref](https://code.claude.com/docs/en/plugins/loading)
- **Node dependencies:** installed automatically only from a lockfile, with `--ignore-scripts`, registry packages only, and a 60 s timeout. [loading ref](https://code.claude.com/docs/en/plugins/loading)
- **Hooks:** about 30 events (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `FileChanged`, `PreCompact`, and others). Handler types: `command`, `http`, `mcp_tool`, `prompt`, `agent`. `PreToolUse` can deny a call or rewrite its input. [hooks](https://code.claude.com/docs/en/hooks)

### Marketplaces, versioning, distribution
- **Marketplace file:** `.claude-plugin/marketplace.json` requires `name`, `owner` and `plugins[]`, and each entry needs `name` and `source`. [marketplaces](https://code.claude.com/docs/en/plugin-marketplaces)
- **Plugin sources:** relative path, `github`, `git-subdir`, `url`, `archive`, `npm`, `command`. [marketplaces](https://code.claude.com/docs/en/plugin-marketplaces)
- **Install:** `claude plugin marketplace add owner/repo`, then `claude plugin install name@marketplace` (or the `/plugin …` equivalents in a session). `claude plugin validate [--strict]` is meant for CI. [marketplaces](https://code.claude.com/docs/en/plugin-marketplaces)
- **Versioning:** the manifest `version` wins, then the marketplace entry `version`, then the 12-character git commit SHA. Pinning `version` keeps users on that version until the string changes; leaving it out tracks commits. Auto-update is **off by default for third-party marketplaces**. Updates apply after `/reload-plugins` or on the next launch. [loading ref](https://code.claude.com/docs/en/plugins/loading)
- **Team rollout:** project `.claude/settings.json` can set `enabledPlugins` and `extraKnownMarketplaces`, but a plugin from an external source is fetched only when user, local, flag or managed settings enable it. Cloud sessions skip a repo's `extraKnownMarketplaces`. [loading ref](https://code.claude.com/docs/en/plugins/loading)

### Limits: plugin vs. a custom harness on the Agent SDK
- **A plugin cannot draw custom UI** in Claude Code. Its interactive surfaces are `AskUserQuestion` (multiple choice), `userConfig` dialogs, MCP elicitation, and text output. A decision form (the inbox) has to live outside the session, for example a local web app or an MCP server that serves a page. My inference from the component list **[unverified as a formal limit]**. [plugin manifest ref](https://code.claude.com/docs/en/plugins-reference), [tools ref](https://code.claude.com/docs/en/tools-reference)
- **A plugin runs inside a session the user starts.** Long-running orchestration across many agents, scheduling, and custom permission callbacks (`canUseTool`) belong to the **Agent SDK** (TS `@anthropic-ai/claude-agent-sdk`, plus Python). The SDK embeds the same loop, tools, hooks, subagents, sessions and MCP. [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- **The SDK can load the same plugin**, but only from a local path (`plugins: [{type:"local", path}]`); it has no marketplace resolution. One plugin can therefore serve both the CLI and a later harness. [SDK plugins](https://code.claude.com/docs/en/agent-sdk/plugins)
- **SDK products must not offer claude.ai login or rate limits** without approval; they use API keys. They must not be branded "Claude Code". Use is governed by Anthropic's Commercial Terms. [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- **Project-scope plugins are restricted:** they need workspace trust, their MCP servers need per-server approval, and their monitors don't load. [loading ref](https://code.claude.com/docs/en/plugins/loading)

## Implications for SDD Studio
1. **Positioning.** No current tool treats a decision as first-class structured data (ID, options, recommended default, status, supersedes) linked both to spec anchors and to tasks. That is the clearest gap to own.
2. **Decision schema.** Build on MADR front matter and statuses (proposed, accepted, rejected, deprecated, superseded) and add `options[]`, `recommended`, `answer`, `answered_by`, `anchors[]`, `tasks[]`. Keep the body immutable and change only the status, as log4brains does.
3. **Question quality.** Borrow Spec Kit clarify's rules: 2–5 mutually exclusive options, a recommended option with reasoning, and a cap on questions per round. Add KanBots-style default-on-timeout as an opt-in, with an audit log.
4. **Amendments.** Use OpenSpec-style ADDED, MODIFIED and REMOVED deltas plus archive as the model for `amend`, and give the change folder a pointer to the decision(s) that caused it.
5. **Rendering.** Produce a static site (log4brains-style) with anchors on every requirement and backlinks to decisions and tasks. Rendering and backlinks are the visible difference from Spec Kit, Kiro and OpenSpec, which ship raw markdown only.
6. **Packaging, step 1.** Ship one Claude Code plugin (`sdd-studio`) with skills `intake`, `research`, `spec`, `decide`, `plan`, `dispatch`, `amend`, `propose-upstream` and `report`. Set `disable-model-invocation: true` on phase-gating skills, `context: fork` on research, and a `PreToolUse` or `Stop` hook to enforce "no code before an accepted plan".
7. **The inbox form cannot live in the plugin UI.** Serve it from a small local web app or MCP server the plugin starts, and keep `AskUserQuestion` as an in-session fallback. Keep state in the repo (decisions as files), not in `${CLAUDE_PLUGIN_ROOT}`.
8. **Portability.** Keep SKILL.md front matter close to the Agent Skills spec where possible so skills also run in Codex, Cursor and others. Spec Kit and OpenSpec show that wide agent coverage drives adoption.
9. **Updates.** Pin `version` in `plugin.json` and release deliberately. Tell users that third-party marketplaces don't auto-update by default.
10. **Harness, step 2.** Move to an Agent SDK harness only when `dispatch` needs fan-out across many agents or worktrees, custom permission callbacks, or headless runs. The same plugin loads there by local path, so step 1 isn't wasted. Address the "too heavy for small tasks" criticism early with a fast path that skips spec and plan for small changes.
